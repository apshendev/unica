# npm dist-tag promotion: staging → потребители → promotion

## Контекст

Замечания 1–3 и 5 ревью npm-контура (`docs/plans/2026-08-25-opencode-issues-2-5-fix-steps.md`,
этап 4): публикация `@apshendev/unica-opencode` двигала потребительский
dist-tag в момент публикации, дымовые потребители ставили пакет до того, как
реестр начинал его отдавать, а доказательство установки не было проверяемым
путём — `opencode plugin` не оставляет проверяемого установленного корня.

## Решение

Контур npm-выпуска становится трёхшаговым:

1. **Stage.** Работа `publish-opencode-npm` публикует кандидата через npm
   trusted publishing под служебным dist-tag `staging` — всегда, и stable,
   и prerelease. После успеха скрипт опрашивает реестр, пока тот не начнёт
   отдавать эту версию байт-в-байт; timeout, мусорный ответ и расхождение
   байтов фатальны. Кандидат выгружается артефактом `opencode-npm-candidate`.
2. **Smoke.** Потребители Windows и Linux ставят точную registry-версию
   через `npm install --ignore-scripts` в изолированном каталоге
   `node_modules` и подключают её абсолютным `file://` URI. Верификатор
   требует, чтобы навыки жили под установленным корнем пакета, а bootstrap
   запускался из `bootstrap/bin/<target>` того же корня; нормализация путей
   следует target, а не ОС прогона. Windows блокирует выпуск, Linux — best
   effort.
3. **Promote.** Работа `promote-opencode-npm` в окружении `npm-promotion`
   со step-level `NODE_AUTH_TOKEN` из секрета `NPM_PROMOTION_TOKEN`
   перепроверяет гейты публикации, сверяет байты реестра с артефактом и
   двигает ровно один dist-tag: `latest` для stable, `next` для prerelease,
   только вперёд по SemVer, идемпотентно, с перечитыванием итога.
   `npm publish` promotion не вызывает никогда.

## Чем это отличается от прежнего решения

`DEC.2026-08-25.NPM-TRUSTED-PUBLICATION` описывал одновременную публикацию
с немедленным consumer-тегом (`next` для prerelease) и дымовых потребителей,
довольствующихся фактом установки. Новый контур разделяет доверие: staged
байты видны только smoke-потребителям, а потребительские теги двигает
отдельная работа с отдельным секретом после их зелёного отчёта. Порядок
`publish → smoke → promotion` доказывается агрегатным тестом, являющимся
`realized` решения; отдельная запись на порядок не заводится.

## Кредициальное разделение

Публикация аутентифицируется короткоживущим OIDC-токеном и не получает
никаких npm-токенов; promotion читает `NODE_AUTH_TOKEN` только в шаге
promotion из environment-секрета `NPM_PROMOTION_TOKEN`. Scope токена и
защита GitHub Environment — живое evidence внешнего этапа настройки, в
статическую заявку не входят.

## Цена

Одноразовая служебная версия `0.0.0-bootstrap.1` под dist-tag `bootstrap`:
без существующего пакета реестр не отдаёт `dist-tags`, которые читает
promotion. Процедура сборки bootstrap-версии и живая настройка доверия —
внешний этап 7 release-runbook'а. Недоказуемое статикой «не удаляет тег и
ассеты» остаётся прозой: pipeline не содержит операций удаления.

## Что не меняется

Двухфазная публикация маркетплейсов Codex/Claude, идентичность MCP-сервера,
упаковка кандидата, поверхность `unica.*`.
