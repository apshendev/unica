# Сужение заясок правил до доказанного

## Контекст

Замечание 8 ревью (`docs/plans/2026-08-25-opencode-issues-2-5-code-review.md`)
нашло десять действующих записей, чья формулировка шире их единственной
проверки: запись заявляет несколько независимо нарушаемых обязательств, а
падает её адрес ровно по одному. Такая запись утверждает то, что сборка может
опровергнуть молча — обязательство без проверки не ловит регрессию и не
мешает ей.

Три npm-записи из десятка уже сужены этапом 4 решением о dist-tag promotion.
Этот дизайн закрывает остальные семь и собирает целостность отображения всех
десяти в один агрегатный тест.

Полные символы, точные адреса проверок и области действия — во front matter
записей и в таблицах этапа 5 плана исправлений; агрегатный тест
`test_the_ten_widened_rules_are_replaced_by_narrow_successors` держит
отображение целиком: ни одна старая запись не забыта, ни одного лишнего
преемника нет, у каждого преемника один независимо нарушаемый адрес.

## Что не меняется

Наблюдаемая форма контрактов не меняется — сужаются заявки записей, а не
поведение. Часть прежних формулировок переезжает в прозу решений и не
является больше проверяемым обязательством реестра:

- положительный выбор платформ (Windows x64, Linux x64) — проза решения об
  адаптере; запись заявляет только отказ неподдерживаемым комбинациям;
- умолчание происхождения ядра и «третий адрес требует новой записи» —
  проза решения о происхождении ядра; контракты заявляют соответственно
  явный вход сборки, байты умолчания и отказ по рассогласованию;
- происхождение общей поставки и отсутствие нативных обёрток — проза
  решения об адаптере; запись заявляет только один плагин с единственным
  хуком `config`;
- происхождение npm-источников из отслеживаемых файлов без симлинков —
  проза решения; контракт заявляет точный состав кандидата;
- фактическое отсутствие потолка версий клиента OpenCode — проза решения;
  запись заявляет только задокументированный пол.

## Честность доказательств

Оба теста этапа версий, скорее всего, зелёные сразу: бампер уже рендерит
все файлы до первой записи. Дефект — недостающее доказательство, а не
поведение: красный воспроизвести нельзя, компенсация — закрытие пробела
тестами и разделение правил. Искусственное падение не создаётся; факт
немедленного зелёного фиксируется здесь и в описании PR.

Полная инвентаризация npm-кандидата при переписывании теста состава нашла
третий класс намеренных отличий, пропущенный прозой плана: тонкий корень
несёт VCS-ignore файлы (например, `skills/.gitignore`), и упаковщик
сознательно удаляет их из staging, чтобы они не правили правила упаковки
самого npm. Тест кодирует этот класс явно — удаления ровно ignore-файлы, —
а контракт состава заявляет его наравне с переносом и преобразованием
README.
